# Requirements Quality Rubric

## Criteria for High‑Quality Requirements

### 1. Unique, Stable ID
- [ ] Each requirement has a unique identifier (e.g., FR-001, NFR-001).
- [ ] ID remains unchanged unless the requirement is removed.

### 2. Specific, Observable Language
- [ ] Requirement describes observable system behavior or property.
- [ ] Avoids vague terms (fast, easy, robust) unless they are defined by measurable criteria.

### 3. Testable Acceptance Criteria
- [ ] Acceptance criteria are clear, concise, and can be verified by a test or inspection.
- [ ] Criteria are written in Given/When/Then or similar format where appropriate.

### 4. Traceability
- [ ] Requirement links to source evidence (user interview, metric, regulation).
- [ ] Requirement links to design element(s) that satisfy it.
- [ ] Requirement links to test case(s) that validate it.

### 5. Necessity & Appropriateness
- [ ] Requirement is justified by a user goal, business objective, or regulatory constraint.
- [ ] Requirement is not gold‑plating; it is the simplest that satisfies the need.

### 6. Consistency
- [ ] No conflicting requirements (same ID with different statements).
- [ ] Terminology is consistent with glossary or domain model.

### 7. Feasibility
- [ ] Requirement is technically feasible given known constraints.
- [ ] Dependencies are identified and reasonable.

### 8. Status Tracking
- [ ] Requirement status (proposed, approved, blocked, etc.) is visible and updated.

**Scoring**: Each criterion met = 1 point. Higher score indicates higher quality.

---
*Use this rubric to review requirements documents, user stories, or specification sections.*
